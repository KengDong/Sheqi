# Prose Bible V1 Proposal｜总编终审

## 0. 总裁决

**内容方向通过，可以冻结为正文生产规则。**

它已经成功把前一轮热门作品研究转成《舍弃》自己的机制，而不是继续保留“像谁”的拼贴指令。

尤其建议原样保留：

- 第三人称近距离限知，默认陆野；
- 动作 / 具体物优先；
- 旁白不做第二个段子手；
- 设定优先动作化；
- 幽默只分“轻 / 中 / 收声”；
- 真正代价场主动收声；
- 人物记录“注意力优先级”，不做固定口头禅；
- 陆野早期把抽象问题翻译成用途 / 钱 / 风险；
- 场景级扩写；
- 独立 Prose Editor；
- 整章接缝修订；
- 遮名测试；
- 结构盲读与文本盲读分开。

但正式落成 `meta/PROSE_BIBLE.md` 前，需要3项执行层修订。

---

# 1. 最大问题：Proposal 太长，不适合作为每章必读的操作Bible

当前 Proposal 约1500行。

内容大多正确，但如果未来每个写作GPT都整份读取，会出现两个副作用：

1. 提示负荷过高，模型开始“表演遵守规则”；
2. 人物对白、幽默、段落都会变得过于自觉，反而有另一种AI味。

## 正式落地建议

分成两层：

### A｜`meta/PROSE_BIBLE.md`
只保留真正的硬执行规则，建议控制成一个可快速重读的核心文件。

至少包含：
- 全局声线；
- 三档幽默；
- 旁白红线；
- 角色注意力入口；
- 陆野内心规则；
- 重场禁区；
- 正文生产SOP；
- Prose Editor核心检查；
- 章尾 / 非标准化原则。

### B｜扩展 Playbook / Appendix
把以下放到非必读附录：
- 30项详细检查表；
- 长篇解释；
- 示例；
- 模板；
- 为什么这样做的研究理由。

正文模型默认读A；
编辑模型按需读B。

这不是删研究成果，而是降低执行噪音。

---

# 2. “600—1500字场景扩写”只能是操作默认，不是篇幅硬门

这个范围适合防止整章一键直出。

但不能让写作AI为了凑到600字：
- 给一个200字就够的小动作硬扩；
也不能让一个自然需要1700字的复杂场景被强行切断。

正式Bible应写成：

> **优先按单场景 / 单局部目标扩写；600—1500字只是常用工作区间，不构成文学硬配额。**

真正硬约束的是：
- 一次只解决一个主要局部目标；
- 不自动扩剧情边界。

---

# 3. Prose Editor 的“盲主题”原则通过，但必须保留章卡结果状态

Proposal 已经基本做到。

正式规则建议明确：

Prose Editor 不知道：
- 作者想表达什么哲学；
- 希望读者感动 / 好笑到什么程度。

但必须知道：
- 当前场景在章卡里要把状态从A变到B；
- 相关人物关系；
- 当前幽默档位；
- 必要Canon边界。

否则编辑器可能为了“更自然”删掉真正必须完成的结构动作。

---

# 4. 人物注意力优先级｜PASS

这部分是 Proposal 最成熟的内容之一。

尤其正确的是：

> **不能每场触发。**

建议正式冻结。

陆野的长期核心也抓得很准：

> 他不轻易接受别人已经替他下好的“没用”结论。

这比“爱捡破烂”更耐写。

---

# 5. 幽默规则｜PASS

“轻 / 中 / 收声”足够。

不再保留：
- 每千字笑点数；
- 每章包袱数。

特别支持：

> 收声不是突然换成严肃文学，而是不主动找包袱。

这正适合《舍弃》。

---

# 6. 正文SOP｜PASS

建议作为正式默认流程：

> 场景脊柱
> -> 关键动作 / 少量关键对白
> -> 写作AI场景级草稿
> -> 独立 Prose Editor
> -> 整章接缝修订
> -> 遮名测试
> -> 结构 / 文本盲读
> -> 作者批准关键位置

不建议退回“AI一次生成整章，作者全文润色”。

---

# 7. 最终建议

**Approve with execution revisions。**

作者需要拍板：

1. 是否批准 Prose Bible 内容方向；
2. 是否同意正式落地时拆成“核心Bible + 扩展Playbook”两层；
3. 是否把600—1500字降为常用区间而非硬配额。

建议三项全部批准。
